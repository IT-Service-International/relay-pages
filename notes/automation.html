Automation Without Losing Control_

NOTE 006 / ENGINEERING PRACTICE / 2026-11-11

Design explicit states, safe retries, accountable decisions and a recoverable exception path.

An automated action still needs an accountable owner.

Automation can move information faster than a team can correct it. A workflow that copies a request, sends an approval and updates a register may look simple, yet every boundary can introduce delay, duplication or ambiguity. The engineering task is to make the process understandable when one of those steps fails.

01 / Define the process before the trigger

Start with the decision and its owner. State what makes a request valid, who can authorize it, which record is authoritative and what counts as completion. A flow diagram should expose rejected, expired and failed requests as clearly as successful ones. Avoid using an email notification as the only evidence that business state changed.

DRAFT → SUBMITTED → REVIEW → APPROVED → APPLYING → COMPLETED
                      ↓                     ↓
                   REJECTED             EXCEPTION

Notification status is separate from business status.

In a SharePoint-based resource request, for example, distinguish the submitted allocation from the approved allocation and the allocation actually recorded downstream. An approval is permission to apply a change; it is not proof that the receiving system accepted it. These are design states, not assumptions about any particular platform's built-in behavior.

02 / Design for repeated and delayed events

Treat duplicate delivery and uncertain outcomes as normal cases to handle. Give each request a stable identifier and each intended operation a deduplication key. Before applying an action, check whether that operation has already completed. Keep the decision and its recorded outcome together where the underlying system permits an atomic operation.

A timeout does not establish that a remote write failed. Reconcile the destination using the request identifier before retrying. For systems without atomic deduplication, serialize work or use a durable operation ledger and an explicit reconciliation step. Do not claim exactly-once behavior merely because the trigger ran once in a test.

03 / Preserve the meaning of approval

Bind approval to the version of the request that was reviewed. If cost, dates, scope or recipients change, decide whether a new approval is required before applying the change. Recheck the relevant preconditions at execution time so that an old approval cannot silently authorize a different action.

Use a managed execution identity with only the access the process needs. Document its owner and renewal path. Keep credentials out of list fields, screenshots and runbooks. Separation between requester, approver and executor should follow the process risk, with exceptional overrides recorded and reviewable.

04 / Make exceptions operable

Use bounded retries for temporary failures. Route persistent failures to a named queue with an owner, a reason, the last completed step and a safe next action. A stopped flow without an accountable queue is a hidden backlog. Alert on age and impact as well as failure count.

  • Record the request ID, version, actor, decision and timestamps.
  • Retain enough evidence to reconcile a partial write.
  • Provide a pause point before further external changes.
  • Define compensation or manual correction for irreversible effects.

A rollback of workflow code does not unsend a message or reverse a payment. Recovery instructions must describe the business correction separately from restoring the previous automation version.

05 / Test the uncomfortable paths

Exercise duplicate requests, late approvals, revoked access, changed records and a timeout immediately after a downstream write. Confirm that an operator can identify the outcome without replaying blindly. Promote a known version with a small initial scope, watch exception age and reconciliation results, and keep a way to stop new work.

Automation earns trust when the team can explain what happened, who authorized it and how to recover. A shorter happy path is useful only when its failure paths remain under control.
