Infrastructure Is a System_

NOTE 005 / ENGINEERING PRACTICE / 2026-11-11

Map the service path, expose shared dependencies, and verify recovery at the user boundary.

A healthy component does not prove a healthy service.

A user sees a successful request or a failure. Between those outcomes sit name resolution, routing, identity, compute, storage and application state. Each team may report its component as available while the complete path remains broken. Engineering begins by describing that path and the evidence needed to trust it.

01 / Start at the service boundary

Choose one concrete transaction: a colleague signs in, opens a project record and saves a change. Record where the request enters, how identity is established, where data is read and written, and how success reaches the caller. Include supporting services such as time, certificates and secrets. A diagram of server names alone misses the relationships that decide whether the transaction works.

Shared dependencies: time / certificates / power / control plane

For every dependency, record its owner, its failure signal and the consequence of losing it. Distinguish what is required for a running service from what is required to start, scale or recover it. A workload may continue during a control-plane outage and still be impossible to rebuild.

02 / Find shared failure domains

Two instances are not independent if they share a storage array, an upstream link, an administrative account or a single recovery operator. Trace common dependencies before calling a design redundant. Ask what survives the loss of a host, a site and the primary identity service. State the scope of each answer; resilience to one failure says little about another.

For example, moving an application to a second site can preserve compute capacity while leaving both sites dependent on the same resolver or authentication path. Test the complete login and data transaction from the recovery location. A successful ping establishes only a narrow observation.

03 / Separate observation from diagnosis

During an incident, retain the time, source and scope of each observation. “The service responds from one subnet” differs from “all users can authenticate.” Build a timeline before assigning a cause. Compare a failed transaction with a successful one and locate the first boundary where their behavior diverges.

  • Check the user's outcome and the application's error.
  • Correlate name resolution, connection, identity and data access evidence.
  • Record missing evidence as unknown, not healthy.
  • Change one bounded hypothesis at a time and verify its effect.

04 / Make recovery a design input

Define the acceptable interruption and data loss with the service owner. Use those requirements to choose recovery arrangements and test scope. A backup job's success establishes that a job completed; a recovery exercise must establish that the data can be restored, opened and used consistently by the application.

Keep recovery access and instructions available when the main service is unavailable. Establish the restoration order from dependencies, including how the recovery environment obtains identity, names and secrets. Avoid a circular plan in which the only instructions or credentials needed to restore a platform live inside that platform.

05 / Leave evidence the next engineer can use

A useful system record contains a service boundary, a dependency map, named owners, known failure domains and the results of the latest recovery exercise. Record the scenario and limits of each test. “Recovered in a lab with prepared credentials” is valuable evidence when its conditions are explicit.

The next change should update that record. Infrastructure becomes understandable when its relationships, failure behavior and recovery path can be inspected by someone who did not build it.
